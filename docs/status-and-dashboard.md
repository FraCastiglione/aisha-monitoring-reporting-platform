# Project Dashboard status and data

The signed AISHA Grant Agreement is the source for formal project start, 48-month calendar, Work Package and Task assignments, deliverables, milestones, the 17 potential risks and KPI targets. The coordinator-confirmed voluntary associated-partner commitments in Attachment 6 supplement Task reporting routes without changing Annex 1. The separate `dashboard-data.json` stores the coordinator's status updates, published messages and reviewed measurements. After editing a public dashboard JSON source, regenerate `assets/embedded-data.js` with `python3 scripts/embed-data.py`; the page uses this generated copy so dashboard and KPI browsing do not depend on runtime JSON fetches. The September 2026 seed records three deliverables as **submitted** and five milestones as **achieved**, as reported by the user; it does not claim formal acceptance or independent evidence verification. `status_as_of` preserves when those facts were last supplied, even if a later intake candidate advances its preparation date and project calendar month.

## Status and reporting coverage

The private register uses `not_started`, `draft`, `submitted`, `changes_requested`, `resubmitted`, and `accepted` for a **whole partner Task report**, identified by `{partner}:TASKS:{start}:{end}`. The coordinator's `compile-dashboard.mjs` accepts only the registered revision of a structurally valid JSON file and writes a private candidate. It counts unconfirmed files and stops if two accepted reports cover the same partner and Task on overlapping days within shared selected months. The published dashboard file receives the candidate only after human review. The private coordinator tools and intake instructions are not included in this public repository.

Each sanitized `reporting_records` entry is either `kind: "task"` or `kind: "work_package"` and contains its Agreement ID, partner code, whole-report receipt status, completed/no-work declaration, and exact coverage dates and selected months. A Work Package summary aggregates its partners' **assigned Task entries** and displays the Work Package leader's own leadership update separately. A leader's assessment of another partner's Task is never counted as that partner's report. Records can cover only some months or days of the chosen dashboard window. An eligible partner without a matching record is **No report recorded**, not automatically late or incomplete: the dashboard has no formal monitoring-request scope or prior-report history beyond the supplied collection.

## Risks and indicators

The 17 Agreement risks are potential risks, with their original impact, likelihood and related Work Packages. Their card mitigations are labelled as summaries; they are not the full signed risk wording. They do not automatically flag each Task in those Work Packages. `task_flags` contains coordinator flags, at-risk/delayed Task assessments from accepted Work Package leader updates, or medium/high/critical significant issues from accepted partner Task reports. Narrative details stay private. The dashboard keeps these distinct.

Agreement KPI targets are shown without invented actuals. The catalogue includes all nine SMART objectives and 19 rows of the call KPI table from PDF pp. 113–115, 24 communication table rows from pp. 137–138, 13 measurement-framework blocks from pp. 122–123 and 26 additional Task, dissemination and impact passages, mapped to 114 typed reporting fields. Each objective and call row has explicit links to related reportable indicators; these are navigation aids, not a claim that one measurement alone fully establishes an objective. Their conflicting dissemination reach, women-beneficiary and DSJP timing figures are displayed together with source notes until the coordinator defines the measurement basis. Partner files may include typed `kpi_contributions` with evidence references and self-reported Nextcloud proof status. `kpi_values` accepts reviewed project totals and optional partner breakdowns by matching KPI ID; importing a partner file never updates public actuals automatically. Text narratives are not converted to counts. Partner values should not simply be summed for unique people, audiences, media items, shared activities or rates; deduplication and numerator/denominator checks occur before adding a project total. No missing measurement is displayed as zero.

The site has no Nextcloud sync or automatic publication of partner files. Sensitive deliverable contents, contributor contacts and report narratives remain outside the dashboard snapshot. A separate private KPI review queue can hold pending and reviewed claims, with evidence references and warnings about a shared activity reference across partners; it never updates public actuals automatically.

## Agreement detail and planning calendar

The dashboard reads full Work Package objectives and Task wording from `assets/agreement-content.js`. Deliverable descriptions and milestone means of verification are transcribed from Annex 1 into `assets/dashboard-detail.json`. The overview's totals use all 22 Agreement deliverables and 23 milestones; its upcoming list covers the six project months after the snapshot month and includes scheduled Task and Work Package starts.

The Gantt uses the Agreement's month-level activity windows and due months across M01–M48, with an expanded display option and two additional post-project closeout columns, M49–M50. The coordinator's deadline rule places each deliverable and milestone on the final day of its Agreement due month; the Agreement itself specifies the month. The first day of the due month is the internal draft review checkpoint. Historical items keep both markers for schedule reference even when already submitted or achieved. User-supplied coordination planning places Technical Progress Report preparation in M19–M20 for RP1 (M01–M18), M37–M38 for RP2 (M19–M36), and M49–M50 for RP3 (M37–M48). These review months appear as purple upper and lower rails around the existing activity bars in relevant Work Package and Task rows and in month headers, not as separate Tasks or exact-date deadlines. The calendar describes the month-long review activity without assigning artificial preparation or completion dates. The project duration stays 48 months and the partner reporting builder stays M01–M48. A future `task_report_deadlines` entry may supply a coordinator-set `id`, exact `due_date` and optional `partner`; the array is empty until a monitoring schedule is agreed. A Task report due on the first of a month gets a draft checkpoint on the first of the prior month. Existing Task report records are shown as coverage for a month, never assigned an invented receipt date. The 20–21 May 2026 kickoff at La Sapienza facilities in Rome and the 18–19 November 2026 Brussels consortium meeting are coordinator-supplied events in `project_events`, separate from Agreement deadlines. They appear in the month headers and calendar agenda without vertical lines crossing the Work Package and Task rows.

The message board reads the `messages` array in `dashboard-data.json`. Each published message may include `date`, `title`, `body`, `author`, `priority` (`urgent`, `important`, or standard) and an optional HTTPS link. The public site is read-only: the coordination team publishes changes by updating the dashboard data and deploying the site. The seed contains no fabricated announcements.

Work Package cards count Tasks that have at least one coordinator-confirmed partner entry. This is reporting coverage, not implementation completion. Verified Task completion is shown only from optional, reviewed `task_progress` entries with state `completed`; without such entries, completion remains **Not assessed**. Deliverable submission and milestone achievement do not automatically complete an ongoing Task or Work Package.
